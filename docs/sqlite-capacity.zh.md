# 家庭网络 365 天 SQLite 容量与性能

## 结论

- 本次新增的厂商、协议、域名/IP 端点、识别质量、Unknown 候选与可用性聚合，在默认分层保留策略下约 `541 MiB`。
- 若把“域名/IP 小时统计”从默认 90 天提高到 365 天，同一模型约 `807 MiB`；Top 10 的全年查询仍走日表，约 `23ms`。
- 加上 Neko Master 原有 7 天分钟明细、30 天完整小时明细、累计表、索引和 WAL 后，典型数据库预计 `3–7 GiB`。
- 建议为在线数据库预留 `20 GiB`；连同一次备份和升级临时空间，建议 QNAP 预留 `30 GiB`。
- 不建议把 `hourly_dim_stats` 完整明细保留 365 天；高基数域名/IP/终端交叉维度会明显放大体积。

## 可复现基准

运行：

```sh
pnpm --filter @neko-master/collector benchmark:home-sqlite
```

| 假设 | 数值 |
|---|---:|
| 历史周期 | 365 天 |
| 活跃终端 | 20 台 |
| 每终端每小时活跃厂商 | 3 个 |
| 每个活跃厂商每小时协议 | 2 个 |
| 每个活跃厂商端点 | 3 个 |

| 查询 | 耗时 |
|---|---:|
| 365 天厂商总量 | `437.14ms` |
| 365 天终端×厂商 Top 500 | `684.21ms` |
| 365 天厂商×协议 | `1,620.97ms` |
| 单厂商 365 天 Top 10 域名/IP（日表） | `21.95ms` |

把域名/IP 小时统计改为 365 天时，共 `4,413,940` 行，数据库
`846,028,800` bytes（约 `806.8 MiB`）；Top 10 日表查询为
`22.70ms`。这说明保留一年的厂商级历史和端点 Top 10 没有压力，
真正昂贵的是无限保留原始连接、分钟统计或所有小时端点。

这些是本机 NVMe 上直接扫描全年小时表的偏保守合成结果，不等于 QNAP 实际延迟；QNAP SATA/RAID、同时运行的容器和 WAL checkpoint 都会影响结果。页面默认查询短时间范围，跨年度查询使用更小的日表；所有查询均受 `(backend_id, time)` 或 `(monitor_id, time)` 索引约束，规模远小于完整域名事实表。

## 容量放大因素

- 活跃终端数与“每终端每小时活跃厂商数”近似线性增加厂商小时行数。
- 域名/IP 小时表还与“每终端每厂商每小时活跃端点数”近似线性增长；日表负责长期 Top 10，因此默认只保留 90 天小时端点。
- 原有 `minute_dim_stats`/`hourly_dim_stats` 的域名、IP、规则、链组合才是主要空间来源。
- SQLite WAL 在高写入期可能短暂增加额外空间；备份和升级还需要一份数据库大小的空间。
- `VACUUM` 会临时需要接近一个数据库文件的可用空间，不应在磁盘接近满载时执行。

## 性能控制

- 写入仍走 `batchUpdateTrafficStats` 单一事务，每 30 秒批量刷新。
- 厂商规则每个批次加载一次，并编译为 exact/suffix Map；匹配复杂度与域名标签数相关，不再随 6,000 多条规则线性增长。
- 自动目录先完整下载到内存、去重并隔离跨厂商冲突，随后在单事务中替换，失败保留最后一次成功规则。
- 厂商小时/日表即使启用 ClickHouse 也写 SQLite，确保年度统计独立可用。
- 可用性原始检查只聚合到分钟/小时，不保存 365 天逐次心跳。
- “永久”是明确支持的配置值，不使用超大天数模拟。永久保留分钟级或原始连接会持续线性增长，界面提供该选项但不作为默认值。
- 所有长查询都有结果上限；SQLite 使用 WAL、64MB 默认缓存和 busy timeout。
